# PDF 连续缩放：方案评估

日期：2026-09-10。决策问题：在保留 Reade 桌面阅读能力与安全边界的前提下，如何解决连续 Ctrl+滚轮掉帧？

采用 decision-analysis 快速通道：本次只选择可撤回的验证原型，不决定更换内核或全面迁移；评估截止为本次答复。建议非最终实施决定。

## 建议

优先验证「视口及邻近区域的位图合成预览 + 手势结束后一次布局提交」。保留 PDF.js 解析和渲染内核，以及现有 Reade 标注、受控外链、Range IPC。随后按测量结果补统一绘制调度和画布预算。

这是基于现有证据的候选最优路线，尚未实现或证明性能优于所有替代方案。

## 依据与限制

- 用户反馈是连续滚动时画面掉帧、跟不上，不是滚轮刻度跳变或只在结束时卡顿。
- 现有 paintLiveZoom 每帧修改祖先 --pdf-live-page-width，然后读取页面几何并恢复滚动；所有页面框均消费该宽度变量。即便高清重绘被延迟，样式和布局工作仍随文档页数增长。
- 上一轮独立 Chromium、500 页合成文本 PDF、120 次逐帧输入的单次样本：原始样式重算 831 次、布局 334 次；减少隐藏文字排版、全页定位扫描及滚动样式切换后，两者约为 122 次。样本不是受控多轮统计，也不是用户实际文件的 WebView2 性能证据。
- 页面目前通过各自 React effect 发起 render；加入绘制队列有利于高清阶段，但不能独自消除手势预览期间的全局布局。
- pdfjs-dist 6.2.108 的组件入口导出 PDFPageView/PDFViewer，没有直接导出 PDFRenderingQueue。PDFPageView 有 drawingDelay、画布限制和 detail canvas 能力，但仍需要适配现有文字、链接、标注和区域截图层。

## 选项对照（工程判断，非实测排名）

| 方案 | 对连续缩放瓶颈的覆盖 | 成本与主要风险 | 选择 |
| --- | --- | --- | --- |
| 保持当前实现 | 已降低重复计算，仍每帧改全页宽度 | 无迁移成本，但手感问题可能持续 | 基线 |
| 只补渲染队列、继续调延迟 | 主要改善高清重绘，不消除全页重排 | 局部改动，但可能错过主要瓶颈 | 后续配套 |
| 有界位图预览，结束时一次提交 | 直接隔离手势帧与全局布局 | 需验证跨页、缩小露边、混合尺寸、双页和坐标恢复 | 优先原型 |
| 迁移 PDFPageView/PDFViewer | 有完整的页面生命周期与调度机制可借鉴 | DOM/CSS、标注、截图引用、外链与可见区域更新均需适配；不保证布局瓶颈消失 | 同机对照与备选 |
| 更换原生 PDF 内核或整套阅读器 | 可能改变绘制能力，但尚无证据表明 PDF.js 解析是主要瓶颈 | Rust/前端契约、安装包、文本定位、安全与维护范围扩大 | 本轮不选 |

## 原型边界

1. 手势开始只测量一次视口和锚点；复用当前已渲染页面的位图，准备视口及有限邻区的预览。不得将整本长文档提升成合成图层。
2. 连续输入按动画帧合并，仅更新有限预览元素的位置和变换；真实页面框暂时不变，避免读取全部页面的几何。
3. 位图和邻区必须有明确像素、内存与数量上限。持续缩小时即将超出缓存范围，应重建有界预览或回退，不能露出空白，也不能无限扩展画布。
4. 结束时一次提交页面布局和滚动锚点，保持旧位图直到新结果可见。文档切换、模式切换、窗口缩放、失焦和卸载均须取消会话并恢复交互。
5. 高清渲染当前可见页优先，有限邻页随后；过时倍率任务取消。按需使用 renderTask.onContinue 协作让出执行，具体并发数由测量决定。
6. 所有预览仅使用本地已有 canvas，不读取新资源；暂停预览期间的选择/链接/截图操作，结束后恢复。不得启用 PDF 脚本、表单执行或无确认外链。

## 成立条件与验收

在同一 WebView2、窗口尺寸、DPR 和文件位置，对比现有基线、有界预览原型和最小 PDFPageView 对照。

- 用用户实际出现问题的 PDF，加 500 页文本、扫描图片、复杂矢量、混合尺寸/旋转及双页样本；先预热，再至少重复三轮。
- 记录输入到下一次呈现的延迟、帧间隔 p50/p95、长任务、布局/样式耗时、高清完成时间和峰值内存。
- 建议门槛（待验证）：60Hz 设备连续缩放 p95 帧间隔不超过 20ms；不能以明显增加高清等待、模糊持续时间或内存换取通过。记录用户实际设备结果，不从独立浏览器推广为真机保证。
- 锚点误差不超过 1 CSS px；无闪白、缩小露边或末页跳动；文字选择、标注命中、内部跳转、外链确认、区域引用和主副栏均通过。

如果有界预览在相同测试中不能明显改善帧延迟，或其跨页/缩小缓存处理成本超过收益，重新评估 PDFPageView 迁移。若追踪显示瓶颈实际在位图上传或复杂页面重绘，再提升画布预算/局部高清渲染的优先级。

## 实施记录（2026-09-10）

用户确认后已实现：

- `src/lib/pdfZoomPreview.ts`：一次有界快照，每帧只做变换；最多 4,194,304 像素（RGBA 像素存储约 16 MiB，不包含 GPU/浏览器副本），最多 16 页参与。二分定位附近页，避免每次手势测量全书。覆盖不足或页面未就绪时回退现有路径。
- `src/lib/pdfRenderQueue.ts`：文档级优先队列，一次一个页面任务；取消过时任务，取消未完成 getPage 也能让队列继续。单页最多 8,388,608 像素、单边 8192 像素；正常页面保留 DPR，上限触发时降低栅格密度。
- `PdfReader.tsx`：提交时统一布局；已有画面保留至新图完成；渲染任务在缩放期间协作暂停。跳页/模式/文档切换取消预览，失焦/窗口或容器尺寸变化提交缩放，清理定时器及快照。
- `app-formats.css`：隐藏原页面并显示有界预览；混合尺寸页面在布局回退时保留自己的宽度比例。
- 原有路径权限、外链确认、标注 DTO 和 Rust IPC 未修改，无新增依赖。没有迁移到整套官方阅读器，也没有实现局部高清瓦片。

### 性能证据

测试代码与截图位于被忽略的 `output/pdf-perf/`。它直接挂载正式 PdfReader；合成 PDF 字节在内存中生成，Range 读取在测试模块层替代，未测磁盘/IPC 吞吐。不是完整 App 所有面板同时开启时的性能，也不是用户真实文件结果。

每轮 120 次按动画帧发送的交替缩放输入，500 页文本 PDF。帧间隔通过 requestAnimationFrame 采样，不是硬件呈现延迟或端到端输入延迟。结果未换算成显示器 FPS。

| 环境/方案 | 三轮 p95 帧间隔（ms） | 超过 25ms 的帧数 |
| --- | --- | --- |
| Chromium，修改前现有实现 | 25.4 / 26.2 / 25.9 | 7 / 9 / 9 |
| Chromium，有界预览原型 | 4.4 / 4.3 / 4.3 | 0 / 0 / 0 |
| Tauri WebView2，关闭快照的布局回退基线 | 27.5 / 19.1 / 21.0 | 18 / 1 / 2 |
| Tauri WebView2，启用快照的最终路径 | 4.6 / 4.3 / 4.7 | 0 / 0 / 0 |

WebView2 基线通过测试浏览器的模块响应替换，让 createPdfZoomPreview 返回 null；正式文件未被替换，队列等代码保持一致。两组各三轮，非随机交错统计，存在热身和系统负载差异。

还挂载了最小官方 PDFViewer 进行方向性对照：Chromium 单轮 p95 12.9ms，没有超过 25ms 的帧。它的 UI、缩放基准、加载方式与 Reade 不完全相同，不能据此宣称普遍优于官方阅读器；仅说明当前瓶颈不要求先整体迁移。

### 正确性与剩余限制

- 已检查明暗主题、760px 窄窗、双页模式、混合尺寸及旋转页、复杂矢量样本、缩放途中跳页、失焦和模式切换。
- 已检查连续缩小到 50% 能回退并清理状态，已有页面重新可见；文档边界采用滚动钳制避免跳位。
- 预览是临时低清位图，持续缩小超出邻区缓存后恢复布局路径，极端操作不承诺相同帧率。
- 最终完整前端测试 1,555 项通过；TypeScript 检查通过；Rust tests 162 项通过、1 项忽略；Clippy 通过；`pnpm tauri build --no-bundle` 成功生成 release 可执行程序。本轮没有重打 NSIS 安装包。
- 未获得用户实际卡顿 PDF；带真实标注、区域截图、复杂扫描文件的完整真机验收仍需用户文件。峰值进程/GPU 内存、输入到呈现延迟、高清恢复时间尚未做系统量化。
- 专用 Tauri 验收窗口启动时，现有用户数据层报告 Local/Roaming 两份标注库的迁移冲突，未修改这些数据库或迁移代码；不能把该环境中的标注存储视为已验收。
